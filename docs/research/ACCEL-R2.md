# ACCEL-R2: Reusing existing drivers for SDM845 (OnePlus 6) on Redox

Date 2026-10-24. Evidence tags: [W] = confirmed by a web source this session (listed at end); [K] = from background knowledge, not re-verified now. Web searches were shallow (one standard search each); treat [K] items as leads to verify before committing engineering time.

## BLUF
- Redox has no Linux-driver compat layer and its stated policy is not to build one [W]. Only experiment found: a 2023 RSoC project to run a Linux VM on Redox to borrow Linux drivers (aimed at NVIDIA GPU) [W]. No evidence it shipped.
- The closest proven prior art for "unmodified Linux driver as a user-level process on ARM phone SoCs" is **Genode's lx_emul/lx_kit DDE** (PinePhone Allwinner A64 graphics, network, touch, USB) [W/K]. It is the best template to copy, not to adopt wholesale (it is C++/Genode-specific).
- Recommended strategy: **hybrid, small-core-in-Rust + borrowed C where the hardware is irreducibly complex.** Translate/write natively the small register-level drivers (GENI serial/I2C/SPI, RMI4 touch, UFS host glue, clocks/regulators/pinctrl). Host under a Linux-emulation shim (lx_emul-style, in a Redox user process) only the big stateful stacks: ath10k, Q6/APR/ADSP audio, remoteproc/QMI/IPA, and later Adreno/MSM DRM.
- A full Linux-VM approach (Redox RSoC idea) is the fallback for GPU/modem/Wi-Fi if the shim proves too costly.

## 1. FreeBSD LinuxKPI (and OpenBSD/NetBSD)
What it is: a kernel-side shim in `sys/compat/linuxkpi` that re-implements enough Linux in-kernel APIs (kmalloc, workqueues, idr, kref, completions, dma-mapping, pci, netdev/mac80211 "net80211 bridge", DRM helpers) for lightly-patched Linux source to compile as FreeBSD kernel modules [W]. Powers drm-kmod (Intel/AMD GPU) and iwlwifi (and other Wi-Fi ports) [W]. Linux driver code is imported as a separate tree (drm-kmod) tracking a Linux version, with a small diff, rebuilt on each LinuxKPI/DRM bump; breakage when LinuxKPI changes is a recurring cost [W bugs.freebsd.org 257264].
- Scope [K]: LinuxKPI is ~tens of thousands of lines; DRM port needs a particularly wide surface (dma-buf, fences, ww_mutex, i2c, backlight, etc.). Wi-Fi uses a LinuxKPI-802.11 mac80211 compat layer (years of work by Bjoern Zeeb, still maturing).
- Architecture support was historically amd64/i386/powerpc64 for KMS [W, dated]; arm64 DRM is much less mature [K].
- Key caveat for Redox: LinuxKPI is **in-kernel** (shared address space, calls into the host kernel's real primitives). Redox drivers are user-space daemons using scheme IPC; the shim's host would be a Redox *library*, not kernel code. So it is an architectural template (API list to emulate), not code to lift. FreeBSD shim code itself is BSD-2-clause [K], which is reusable licence-wise.
- OpenBSD [K]: has its own "drm" port using a small Linux-compat header layer (`drm_linux.h`) - far thinner, driver code manually kept in sync with Linux (they import roughly 1 Linux release behind). NetBSD [K]: similar `linux` compat headers for drm and Wi-Fi (`sys/external/bsd/drm2`, `linux` shim) - the DRM port was done by the same "emulate headers" method. Both show the pattern: the more drivers you want, the more of Linux you end up re-implementing.
- Effort for SDM845 [K estimate]: a minimal LinuxKPI-equivalent for platform drivers (geni, ufs, dwc3, rmi4) is a few thousand lines of shim; adding mac80211/cfg80211 for ath10k is a large extra (cfg80211+mac80211 are ~100k+ lines in Linux; either emulate or port real code).

## 2. Genode DDE-Linux (lx_emul / lx_kit)
- Original dde_linux (2012-) ran Linux driver subsets (USB, Wi-Fi, etc.) in user-level components with hand-written emulation of Linux APIs. By 21.08 Genode said that approach became too labor-intensive for many ARM SoCs and introduced a new method [W 21.08 release notes].
- New method [W/K]: **lx_emul** - build the *real Linux kernel source files* the driver needs plus a small hand-written `lx_emul` layer; instead of writing emulation by hand, they run the driver, and a tracing tool lists the unresolved symbols; for each, either (a) compile the real Linux file that provides it, (b) provide a short implementation, or (c) generate a stub that logs a "not implemented" message when called (the porting guide says many emulated functions are just link-satisfying stubs) [W]. A force-included `lx_emul.h` carries prototypes; missing headers are auto-symlinked from the Linux tree; rule of thumb "add as few headers as possible" [W]. **lx_kit** (modular backend, [W commit mirror]) provides memory, timers, work queues, IRQ (mapped to Genode IRQ sessions), MMIO/DMA via Genode platform driver, etc. Linux runs single-threaded-ish in one "Linux kernel task" emulation (scheduler emulated with lx_kit tasks) [K].
- ARM phone evidence [W]: PinePhone (Allwinner A64): network (emac), framebuffer/display, touch, USB host/modem/GPIO ported; first success stories of the new way were PinePhone graphics drivers [W 21.08]. Devices are described via device tree; the platform driver hands each driver component its MMIO/IRQ/clocks per DT node [K].
- What they stub [K]: scheduler, RCU (trivial), most of /proc /sysfs, power management, locking mostly no-ops with a cooperative model, debugfs, tracing, module loader, hotplug uevents. What they implement for real: memory (slab/page alloc), timers/jiffies, workqueues/tasklets/irq threads, DMA coherent alloc, clk/regulator/gpio/pinctrl stubs forwarding to platform driver, firmware loading via a ROM/file session, device-tree parsing (`of_*`).
- Applicability to SDM845 [K]: Genode itself has no (or little) mainline Qualcomm SDM845 support; Qualcomm clocks (GCC/RPMh/RPMh-regulators), interconnect (bandwidth votes on RPMh), PD/GDSC, SMMU (arm-smmu qcom impl), and IPC (SMEM, GLINK, QMI) are *infrastructure drivers other drivers depend on*; the lx_emul approach would need those Linux drivers hosted too (since DT bindings reference clocks/regulators/interconnect by phandle). This is the main cost multiplier on Qualcomm vs. Allwinner.
- Licence: the lx_emul code is Genode's (AGPLv3 + commercial; [K]) - not directly reusable by Redox (MIT) without care; but the *technique* is free to copy.

## 3. NetBSD rump kernels / anykernel
- Rump runs unmodified NetBSD kernel components (file systems, network stack, USB, audio, etc.) in an ordinary userspace process, linking against a small host abstraction (`rumpuser(3)`); hosts include POSIX userspace, Xen/KVM and bare metal; BSD-2-clause [W].
- Why it works for NetBSD: the kernel was *factored* (the "anykernel") so drivers depend on well-defined interfaces. Linux was not, so no equivalent "rump Linux" exists except **LKL** (Linux Kernel Library) - Linux compiled as a library for userspace, mainly for network stack/fs, and **UML/libOS (LibOS/DCE)** [K]. LKL runs Linux drivers poorly for hardware (no real MMIO/IRQ exposure); not a path for SDM845.
- Value to Redox [K]: only if a *BSD* driver exists for the hardware. NetBSD arm64 has Qualcomm support? Not for SDM845 [K, unverified]. So rump is low value for this project. Possible niche: NetBSD's USB/audio class drivers (generic, hardware-independent) hosted under rump on top of Redox's xhci - Redox already has native xhcid/usbhidd so little gain.

## 4. L4 DDEKit, seL4, Fuchsia
- **L4 DDEKit / DDE-Linux (Fiasco.OC, TU Dresden)** [K]: predecessor of Genode's DDE; "DDEKit" = tiny C API (memory, IRQ, PCI, timers, threads) with DDELinux26 built on top; used for USB, Ethernet, SATA, PCI drivers on x86. Same lesson: works for well-behaved bus drivers; effort grows per subsystem.
- **seL4 driver VMs** [K]: seL4's CAmkES/Microkit "VM as driver" model puts a Linux guest in a VM with passthrough to the device and exports a virtio-ish interface to the rest of the system. Simple and licensing-clean (GPL stays inside the VM), but costs a whole Linux guest (RAM, boot time), and needs IOMMU/SMMU for safe DMA passthrough. On SDM845 Qualcomm's own hypervisor/EL2 situation matters: on OnePlus 6 the kernel boots at EL1 under no hypervisor typically (Linux mainline boots via fastboot at EL1; EL2 availability varies) - verify before designing a hypervisor-based plan [K].
- **Fuchsia DFv2** [W]: user-space drivers as components, FIDL IPC (Banjo being retired), drivers migrated from DFv1 [W]. Fuchsia does **not** reuse Linux drivers via a shim as policy; drivers are written natively in C++ (now Rust support growing) per board; Wi-Fi uses a mix of vendor-ported FullMAC firmware drivers [K]. I found no source about Fuchsia Qualcomm driver ports [W: search came up empty]; Fuchsia board support is mostly Amlogic/MediaTek/Intel/Broadcom/Qualcomm-for-Pixel-prototypes - unverified [K]. Lesson for Redox: Fuchsia's evidence supports the "write native, small, per-board drivers" approach when you own the framework, but Fuchsia has Google-sized staffing.

## 5. Redox-specific facts
- Official policy [W "Porting Strategy"]: Redox aims to be mostly source compatible with Linux/relibc and says focusing on platform services is better than a Linux translation layer; it explicitly notes drivers/filesystems being Linux-specific and cites FreeBSD's approach as the counterexample - i.e. not adopted.
- RSoC 2023 "Apps and Driver support in Redox OS" [W]: Linux-in-a-VM (Revirt-U) to borrow Linux drivers incl. proprietary GPU; status not confirmed shipped.
- Platform state [W]: AArch64 got initial multi-core support in Aug 2026 reports; io_uring-like ring API (helps NVMe-style drivers); real-hardware boot improvements (ACPI crate; April 2026). Book Raspberry Pi 3 B+ page is flagged outdated. No evidence of device-tree-driven driver probing infrastructure comparable to Linux's `platform_driver`, IOMMU/SMMU support, or clock/regulator frameworks [W: none found]. SDM845 is DT-based, not ACPI (OnePlus 6 boots Linux through DT), so DT support in Redox is a gate.
- relibc/ABI helpers [K]: relibc gives Linux-ish libc/syscall surface for apps (not the kernel ABI drivers use); Redox's existing driver pattern is user-space daemon + `scheme:` files + `iopl/physmap/irq:` schemes (`/scheme/irq`, `/scheme/memory/physical`) - these map neatly to a lx_kit-style backend (MMIO map, IRQ wait, DMA alloc) but DMA-coherent allocation with physical addresses and IOMMU-less safety are the weak points. No kernel work needed for MMIO+IRQ on SoCs without SMMU isolation; with the Qualcomm SMMU, DMA masters must be programmed or placed in bypass.

## 6. C-to-Rust translation (c2rust / LLM)
State of the art [W unless noted]:
- c2rust (rule-based) emits correct but unsafe, non-idiomatic Rust; useful as a mechanical first pass, not a maintainable end state.
- LLM pipelines 2025: **LLMigrate** (arXiv 2503.23791) translated three Linux kernel modules (math, sort, ramfs), required modification of <15% of the target code with GPT-4o + static analysis + compiler repair; **SACTOR** (2503.12511) two-step translate then idiomatic refine with FFI tests; **RustMap** (2503.17741) project-scale, up to ~7k-line bzip2; **Syzygy** (ICSE'25 workshop) ~3k LoC Zopfli with dynamic-analysis feedback. All evaluated on userspace libs or toy kernel modules.
- Gap: I found no published result translating a real hardware driver (MMIO/IRQ/DMA, DT bindings, locking) from Linux to Rust. Rust-for-Linux drivers (Nova, Tyr, Apple AGX, Android Binder) are hand-written, not translated [K]. Consequence: translation of a driver is good for small/self-contained files (<~3k LoC, few kernel-API calls) where tests on real hardware or an emulator register-trace can verify behaviour; it does not remove the need for the *framework* (clock/regulator/IRQ APIs) in Rust.
- Practical technique [K]: use the LLM to translate *from the Linux source + hardware docs/register headers* into Redox-style Rust against a small hand-written HAL trait set (Mmio, Irq, Dma, Clock, Regulator, Gpio), verify via record/replay of MMIO traces captured from Linux on the same phone. This is "reimplementation guided by existing code" and sidesteps kernel-API emulation.

## Driver-by-driver analysis (Linux source -> Redox user-space process)

GPIO-IRQ via TLMM pinctrl irqchip); DMA-coherent memory with known physical address; clock/regulator/pinctrl/GDSC/interconnect providers (Qualcomm GCC, RPMh); timers; workqueues (threads); firmware file loader (`/lib/firmware` equivalent from the device's partitions - note SDM845 firmware blobs are Qualcomm-proprietary, redistribution rights are a separate issue).

## Required shim services, by effort (for an lx_kit-style backend on Redox) [K estimate]
1. Low: kmalloc/slab, jiffies/timers/hrtimer, completions/mutex/spinlock (single-threaded cooperative = no-ops), workqueues/tasklets (thread pool or one thread), device model stubs (`struct device`, `kobject`, `devres`), `of_*` DT API on a flattened tree, `ioremap/readl/writel`, `request_irq` -> scheme:irq blocking thread.
2. Medium: DMA API (coherent buffers need phys addr from Redox memory scheme), clk/regulator/reset/gpio/pinctrl consumers forwarded to a "platform" daemon; firmware loader; platform bus matching.
3. High: IOMMU/SMMU (qcom arm-smmu impl, context banks used by Adreno, UFS?, USB? via `iommus=` in DT), interconnect bandwidth votes (RPMh), power domains, SCM calls into TZ via SMC (EL1->EL3, needs kernel/hypervisor support for `smc` or a trap), sysfs/debugfs, regmap, SCSI/ASoC/mac80211 subsystems.
Redox kernel changes needed for the hosted path [K]: expose SMC/HVC call to a privileged daemon; physical-memory/DMA scheme with contiguous allocations and cache maintenance ops (arm64 non-coherent DMA!); GIC IRQ routing to user processes (exists for x86/RPi-level); optional SMMU management. Cache maintenance on non-coherent DMA is easy to get wrong silently.

## Licensing
- Linux drivers are GPL-2.0 (some dual-licensed GPL/BSD, e.g. many `ath` files are ISC/GPL [K]). Redox is MIT. Running GPL code in a **separate process** that communicates over IPC is generally considered "aggregate" in the FSF/Linux community view as long as it isn't a derivative work - but a shim that *links* GPL driver code together with Redox library code in the same process creates a combined work; the combined binary must be distributable under GPL-2.0 (source offer). That is acceptable for a project that wants reuse: keep GPL driver daemons in their own repo/packages, MIT shim could stay MIT if it contains no GPL code (but headers copied from Linux for the emulation layer are GPL - Genode and FreeBSD both deal with this: FreeBSD ships such compat code under BSD licence and keeps only the Linux driver tree GPL in drm-kmod [W/K]).
- A *translation* (c2rust/LLM) of a GPL driver is a derivative work -> the Rust result is GPL-2.0, even if "idiomatic". Clean-room reimplementation from hardware docs/register traces (not from source) avoids that, but is hard to prove if the LLM saw the source. Decide per driver whether GPL in-tree is acceptable (separate repo with GPL licence, IPC boundary) - get legal review if Redox upstream wants it in-tree.
- Firmware blobs: Qualcomm firmware for SDM845 (`adsp`, `cdsp`, `venus`, `a630 zap`, `wlanmdsp`, Wi-Fi) is proprietary; must be extracted from the user's own device/partitions, not redistributed.

## Ranked recommendation
Bring-up order (what the first boot needs) and approach:
1. **Native Rust (small, necessary, framework-forming):** DT parsing; GIC; PSCI; clocks/regulator/pinctrl/GDSC for GCC/RPMh minimal set (copy tables, not code structure); GENI UART (serial console) and GENI I2C/SPI; TLMM GPIO/pinctrl+irqchip. These form the HAL the shim would later use too, so they are not wasted either way.
2. **Native Rust (translated or rewritten, LLM-assisted with MMIO-trace verification):** RMI4/touch; dwc3 init + hand-off to existing xhcid (host mode); minimal UFS driver (block-level only) + QMP UFS PHY init tables; simple PMIC (SPMI/pm8998 regulators, RTC, power key) drivers.
3. **Host under lx_emul-style shim (second phase, only if staffing allows):** remoteproc + smem/glink/smp2p/QMI (modem/sensor/ADSP enablement), then ath10k *or* decide to rely on USB Wi-Fi.
4. **Defer or VM-route:** Q6/APR audio, Adreno/MSM DRM (a630 GPU), cellular modem/IPA, camera. Use a Linux guest VM with passthrough (RSoC-style/seL4-style) only if the product needs them and Redox gets aarch64 virtualization (KVM-like) support, which is not evidenced [W: none found].
5. **Avoid:** porting rump/NetBSD (no SDM845 hardware drivers); trying to emulate all of mac80211/ASoC/SCSI/DRM in the shim for the first milestone; bulk c2rust of whole subsystems (unsafe output, GPL derivative, no hardware verification).

Decision rule: if the Linux driver is <~3k LoC and touches only MMIO+IRQ+clk/regulator, translate it natively; if it sits on a large Linux subsystem (SCSI, ASoC, mac80211, DRM) hosting it requires emulating that subsystem, so either skip, use a hardware-independent alternative, or use a VM.
